The problem

The Code Works. The Change Is Too Big.

Nobody reviews a twenty-file diff properly at 6pm. So the extra endpoint ships, and you find out what it does three weeks later.

WHAT YOU ASKED

One Small Fix

Handle a duplicate email instead of returning a 500. Three files, one code path that already exists.

WHAT YOU GOT

A New Flow

A new endpoint, pre-submit validation, new client state, a shared utility, a changed API contract.

WHAT IT COSTS

Your Review

An architecture decision you never made, handed to you at the moment you have least context on it.

The difference

It Is Not A Code Graph. It Uses One.

Ichor keeps a graph, but the graph is not the product — it is the evidence. Code-graph tools answer where is this? Ichor answers a question none of them ask.

A CODE GRAPH

Where Is This, And What Relates To It?

Tools like Graphify map a codebase so you can query it instead of grepping. Around 40 languages, your docs and PDFs too. You ask, it answers, you decide. They are good at that, and Ichor is not trying to be one.

ICHOR

Should This Edit Be Part Of This Job?

Not a retrieval question. It runs on every write whether the agent asks or not, it knows what you are working on today, and it has to justify a challenge with a path it can point at. TypeScript and JavaScript only — that is the price of the depth.

IT RESOLVES, IT DOES NOT MATCH

Names Are Bound, Not Guessed

import { send } from './email' plus that module's export list is the answer — so a call becomes an edge to a declaration Ichor can name, through re-exports and namespace imports. Never a same-name coincidence, and never a match inside a comment or a string.

AND IT ADMITS THE GAPS

7,178 Call Sites It Would Not Guess At

On papermark, that many calls could not be resolved to a declaration — so they are counted and reported, not invented. The graph is a floor, never an inflated one. A wrong edge would be quoted back as evidence, and evidence has to be true.

Connected Is Not The Same As Necessary.

This is the difference in one example, and it is the whole reason a graph is needed rather than a search.

Your agent adds /api/vendors/check-email during a duplicate-email fix. Ask any search tool whether it relates to the task and everything says yes — same table, same folder, same service. All true. So relatedness gives you no reason to object.

the question Ichor asks next
the task's existing path: POST /api/vendors ────► createVendor ────► Vendor.email (unique) ▲ the new endpoint: │ POST /api/vendors/check-email ──────────────────┘ reaches the SAME rule by a SECOND road

The database already refuses duplicate emails, and the submit path already reaches that rule. So the endpoint is connected, relevant, and unnecessary — a second enforcement of something already enforced. No amount of retrieval makes that judgement for you. They solve different problems, and you could reasonably run both.

How it works

It Knows What Your Code Actually Connects To.

Not keyword matching. Ichor compiles your codebase into a graph of what calls what, which endpoints reach which tables, and which types everything depends on — then judges edits against it.

1

It reads your repo, once

The TypeScript compiler resolves every call, import, route and Prisma model into a graph stored in a local HydraDB. 25 seconds for 1,362 files, then seconds to keep up.

2

Your prompt draws a boundary

Ichor finds where your task lives and walks outward through real call edges. Name a file and the boundary is that file and its neighbours — 9 functions instead of 135 on a real project. No command to type; it reads the conversation.

3

Edits outside it get questioned

Before the write lands, not after. And it has to show its evidence — the existing path that already does the job, named function by named function.

What it says

It Asks Why. It Never Says No.

A tool that fires on every third edit gets uninstalled the same afternoon. Ichor is built to be quiet — and to lose the argument gracefully when it is wrong.

EXPECTEDInside the boundary. Ichor says nothing at all.
CONNECTEDJust outside, with a real path back. The boundary grows on its own.
SUSPICIOUSNo real connection. Ichor asks why, and shows the evidence it used.
JUSTIFIEDThe agent explained, the codebase backs it up. The boundary grows.
YOUR CALLPlausible but unverifiable. Ichor asks you instead of deciding.

It never blocks a prompt and it never asks twice about the same file. Write the file anyway and it lands — Ichor just remembers that the reason was never given.

All day, one session

Move On, And It Moves With You.

Nobody runs a CLI command between tasks. A boundary drawn at 9am would still be policing vendor code at 2pm while you are deep in billing, arguing with every edit.

Ask a question instead of giving an instruction and the boundary does not move at all — you are not changing anything, so there is nothing to protect.

Ask the graph

Your Agent Gets To Use It Too.

The same graph that judges edits will answer questions. Your agent stops guessing at grep patterns and asks what the compiler already knows.

ICHOR_FIND

Where does this live?

Describe it in plain words — "the place invites are created". It searches structure, so it finds names you could not have guessed and skips matches in comments.

ICHOR_IMPACT

What breaks if I change it?

Callers, the endpoints that end up running it, the tables at stake, and every function depending on a type's shape. One call, no grep.

ICHOR_PATHS

How is this table reached?

Which endpoints, through which functions. Useful before adding a second way to write data that already has one. No file search can answer it.

Asked "what breaks if I delete the useAuth hook?" on a real project, an agent answered with one ichor_impact call and nothing else — no grep, no file reads.

Proof

Measured On Somebody Else's Code.

The number that decides whether a tool like this survives is how often it interrupts work you were right to do. Passing your own tests on your own demo proves nothing about it.

12.8%

Share of edits a developer genuinely had to make that Ichor would have interrupted — about one in eight. Replayed through the real classifier, not estimated.

EVIDENCE
86

Files across 30 real commits from a real product. Each commit message is the task; the files it changed are the truth. Every file type, not just the ones Ichor reads.

SPEED
6s

To catch up after you edit a file in a 1,362-file codebase. The largest repo tested — 7,735 files — is read at Node's default heap.

Every number here is reproducible from this repository. The measurement harness is in scripts/, and the suite that matters most exists because six others passed while eleven real bugs were live — they all ran against an eleven-file demo.

Install

Three Commands, And No Task To Type.

Needs Docker for the local graph database, and a TypeScript or JavaScript repo. Your code never leaves your machine.

your-repo
$ npm i -g ichor-cli $ ichor init # hooks for Claude Code and Codex $ ichor up # local HydraDB, binds to 127.0.0.1 $ ichor watch # reads your repo, then follows the conversation Watching. Run your agent as usual — Ichor picks the task up from your prompts.
WORKS WITH

Claude Code and Codex CLI

Both get the full thing — challenges before the write lands, plus the graph tools. Cursor, Windsurf, Gemini CLI and Cline use the same adapter interface and are next.

NO ACCOUNT

Your code stays on your machine

HydraDB and MinIO run locally through Docker, every port binds to 127.0.0.1, and there is no telemetry. Nothing is uploaded to run Ichor.

RECOMMENDED — UNLOCK THE JUDGE

Add an OpenRouter key and Ichor can weigh an argument, not just the structure.

Every boundary, every verdict, every piece of evidence and all nine tools work with no key at all — that is deliberate, and it is why there is no signup. A key adds the one thing structure cannot do: when your agent argues that an expansion is genuinely necessary, that argument gets weighed against the evidence the graph produced, instead of the question coming to you.

It is cheap on purpose. A small model, called only when an argument has actually been made — never on an ordinary edit — and capped per task and per file. Exercising every path in Ichor end to end costs well under a dollar, so a spare key with a couple of dollars on it is plenty.

Honest limits

What It Cannot Do.

A tool that claims to know where a task belongs should be precise about where it is blind.

  • TypeScript and JavaScript only. Python is next. Nothing else is claimed.
  • It still questions about one edit in eight that you were right to make. Measured, not estimated — and naming the file in your prompt is what makes it precise.
  • A shell write cannot be challenged. Ichor hooks edit tools, so a file written by cat > or a codegen script is invisible in the moment. It is named at the end of the turn instead, so silence never means "nobody looked".
  • Ichor can be wrong. The boundary is an expectation, not a fact. When it cannot verify a justification it asks you rather than deciding — and it never blocks a prompt.

The longer list — memory ceilings, one database per repo, static-analysis blind spots — is in the docs, where it belongs.
