01 / The problem

Agents Are Good At Code. Not At Staying Proportional.

The change usually works. It is just far bigger than what you asked for — riskier, harder to review, and full of decisions nobody made on purpose.

WHAT YOU ASKED

One Small Fix

Handle a duplicate email properly instead of returning a 500. Three files, one existing code path, maybe a test.

WHAT YOU GOT

A New Flow

A new endpoint, pre-submit validation, new client state, a shared utility, a changed API contract, twenty files.

WHAT IT COSTS

The Review

You now review an architecture decision you never made, at the exact moment you have the least context on it.

02 / How it works

A Task Boundary That Comes From The Code.

Not a folder rule. A real task crosses UI, API, service, database and tests — files that share no words and no directory. What connects them is the structure of the program.

1

Read the codebase

The TypeScript compiler resolves every function, call, route and database model. No guessing, and no LLM anywhere near the structure.

2

Store it as a graph in HydraDB

Functions call functions, routes are handled by functions, functions touch models. That graph is the evidence for everything that follows.

3

Take the task from what you asked

You never type a task. Ichor reads the prompt you gave the agent, anchors it to real routes, functions and fields, then walks outward through actual call structure.

4

Watch every edit, stay quiet

A pre-edit hook fires before the agent writes anything. Inside the boundary, Ichor says nothing at all. Silence is the normal state.

5

Challenge, then listen

When work expands, Ichor asks why and shows the path it walked. The agent can argue back over MCP — and the graph, not the argument, decides.

6

Redraw itself between turns

When the agent stops talking, the graph rebuilds in the background. When you type again, Ichor checks whether you are still on the same job.

03 / The two questions

Connected Is Not The Same As Necessary.

A new /check-email endpoint imports your database client, queries the right model, and sits with the other vendor routes. Every connectedness check passes. It is still the wrong change.

TEST ONE

Is It Connected To The Task?

Reachability across the call graph. A new file is judged by what it reaches, never by the fact that it is new — real work creates new files constantly.

TEST TWO

Does A Path Already Do This?

The one nothing else does. If the submit path already reaches the uniqueness constraint, a second endpoint is a second flow for a rule already enforced.

04 / Not a blocker

It Asks Why. It Does Not Say No.

A tool that fires on every third edit gets uninstalled the same afternoon. Ichor is built to be quiet, and to be wrong gracefully when it is wrong.

EXPECTEDInside the neighbourhood. Ichor says nothing.
CONNECTEDJust outside, with a real path back and the same data. The boundary grows on its own.
SUSPICIOUSWeak or no connection. Ichor asks why, and shows the evidence it used.
JUSTIFIEDThe agent explained and the codebase backs it up. The boundary grows.
HUMAN REVIEWPlausible but unverifiable. That is your call, not Ichor's.
05 / All day, one chat

The Boundary Follows The Conversation.

Nobody runs a command between tasks. You fix a bug at 9am and you are somewhere else entirely by 2pm — in the same conversation. A boundary drawn for the morning would spend the afternoon questioning every edit, and you would switch it off by lunch.

one session, hours apart
you › fix the duplicate email crash in vendor onboarding [ichor] task set — 14 functions, data: Vendor you › continue [ichor] nothing changes — that names no part of the codebase ··· hours later, same conversation ··· you › now fix the rounding on billing invoices [ichor] new task — 3 functions, data: Invoice
IT NOTICES

You Changed Subject

A prompt pointing somewhere the boundary does not cover redraws it. One that points inside just carries on.

IT IGNORES

Everything Else

"Continue", "that didn't work", a pasted stack trace, a question. Anything ambiguous changes nothing at all.

IT TELLS THE AGENT

Before It Starts

Each turn begins with the boundary in the agent's context, so over-reach is mostly prevented rather than punished.

06 / Agents

One Layer, Underneath Your Agent.

Ichor is not a plugin for one tool. Hooks make sure the agent cannot forget it exists; MCP lets the agent collaborate with it. New agent, new adapter — same engine.

The agent can also just ask. Before writing a line, a real Codex run searched the repo for five words, got 116 hits and read six whole files — working out which code the task lived in. Ichor had answered that in 14ms and could have simply been asked.

ICHOR_CALLERS

Who Uses This?

Every function that reaches it, and the endpoints behind them. From the compiler, so it finds callers a text search misses and skips matches inside comments.

ICHOR_PATHS

How Do We Reach This Data?

Which endpoints can end up touching a table, and through which function. No file search can answer that one.

07 / Install

Three Commands, And No Task To Type.

Your code never leaves your machine. Ichor runs HydraDB locally, so the graph of your codebase stays on your disk. There is no account.

Run your agent as usual — Ichor picks the task up from your prompts.

Requires Node 20+, Docker, and a TypeScript repo — ideally Next.js with Prisma. Prefer to name the task yourself? ichor start "…" still does exactly that.

08 / Honestly

What It Cannot Do.

A tool that claims to know where a task belongs should be precise about where it is blind.

  • TypeScript and JavaScript only. Python is next. Nothing else is claimed.
  • Static analysis. Dynamic dispatch and runtime-constructed calls are invisible, so results are a floor and never a ceiling.
  • Shell writes cannot be challenged. Ichor hooks the agents' edit tools, and a file written by cat > or a codegen script never announces itself — you would have to predict what an arbitrary command will write. It shows up on the map at the next rebuild, so Ichor catches up; it just cannot ask why in the moment.
  • Task detection can be wrong. It moves the boundary only when a prompt points somewhere the boundary does not cover. ichor status always shows what it decided, and naming a task by hand overrides it.
  • The graph is rebuilt between turns, not during them. Within a single turn it can be a few edits behind.
  • One conversation at a time per repo. Two agent sessions in the same checkout share one boundary.
  • The boundary is an expectation, not a fact. It is designed to grow when the work justifies it.
  • Ichor can be wrong. When it cannot validate a justification it asks you, rather than deciding for you.
